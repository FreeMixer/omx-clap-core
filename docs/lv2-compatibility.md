LV2 compatibility
=================

OpenMixer hosts CLAP and LV2. An LV2 plugin runs natively: it is a real LV2 instance, loaded
through lilv, with no emulation and no wrapper process. In omx-clap-host and in the console's
engine the instance is loaded in process, and `libomx-clap-lv2`, the LV2 adapter this repository
builds, maps the host interface: the plugin's ports and controls are presented as CLAP ports and
parameters, so one hosting core drives both formats. The adapter is that mapping and nothing
more; the plugin's own code runs as it would in any LV2 host. plugin-hostd hosts CLAP and LV2
plugins each in a worker process of its own: an LV2 plugin runs in an omx-clap-host worker (the
first column below, through the daemon), or in mod-host when the adapter refuses it.

Almost all of LV2 is supported: every port type (audio, control, CV, atom and event MIDI, the
ll-plugins MIDI port, time, patch), the port groups and their channel maps, the port properties,
the options, the worker, state with its path features, presets, the latency port, the fixed block
length where the host declares it, the deprecated `uri-map`, `event` and `rtmempool` features that
older plugins require, and the plugin's own bypass. The matrix names the test behind each row. What
is not supported, each for its reason:

- `bufsz:powerOf2BlockLength`, by default: neither omx-clap-host nor the console promises every
  block a length that is a power of two (a PipeWire quantum need not be one), so neither declares
  it, and only a host that pins its block may.
- `bufsz:fixedBlockLength` in the console: the console's engine does not promise one block length,
  so it does not declare it; omx-clap-host does, since under JACK every cycle is the buffer size.
- `instance-access` and `data-access`, refused on purpose: only a plugin's own UI needs them, and
  the console never shows one (GUI ruling 2026-10-19).
- Native LV2 desktop UIs (`ui:X11UI`, `ui:GtkUI`, `ui:Qt5UI`): not hosted. The console draws a
  panel from the plugin's parameters, and omx-clap-host shows a plugin's own window for CLAP
  plugins only. modgui is planned in the console.
- A latency that moves under a parameter sweep is lossy: it is applied after a hold and a restart
  rather than per cycle.

Rows (supported / lossy / refused on purpose / unsupported / not tested; the No GUI row is no feature and is not counted): in-process 53 / 9 / 2 / 3 / 0, plugin-hostd 2 / 0 / 0 / 4 / 61 of the same 67; Through omx-clap-host 15 / 1 / 0 / 0 / 0, plugin-hostd 3 / 0 / 0 / 0 / 13 of its 16.

How to read the matrix
----------------------

- **in-process (`libomx-clap-lv2`)** is the adapter this repository builds, linked into
  omx-clap-host and into the console's engine: the plugin's lilv instance, its ports and
  controls presented as CLAP ports and parameters.
- **plugin-hostd** is the plugin added through plugin-hostd's socket. Its `lv2_worker` setting
  chooses who runs it: `auto` (the default) runs it in an omx-clap-host worker, the first column's
  adapter in a process of its own, and in mod-host when the adapter refuses it; `omx-clap-host` and
  `mod-host` pin one. A plugin in an omx-clap-host worker gets what the first column says, but this
  column says **supported** only where a test of plugin-hostd's runs the feature through the daemon
  and passes on its main branch (plugin-hostd c4be474, CI run 40266105376). **not tested** means no
  such test exists yet, whatever the worker does.
- A cell says **supported** only when a test exercises the feature and passes in CI, and the cell
  names it. The tests are this repository's unless the cell names another one. Run them with
  `make test-lv2`.
- **lossy** means the feature works, but not exactly as the LV2 specification describes it; the
  cell says how it differs.
- **refused on purpose** means a ruling keeps it out; the cell names the ruling.
- **unsupported** means it is not done; the cell says why, and where it is planned.
- `tests/clap_lv2_identity.sh` runs one plugin through mod-host as the reference of the
  omx-clap-host rows below; it proves the output, not the features.

| A MIDI source: a MIDI output and no input of any kind (an arpeggio or sequence generator) | supported as a pass-through tool: the strip's pair passes through untouched (`passthrough: host`), its notes on the CLAP note output (`lv2_host_test` sources, `lv2_clap_test` generator); omx-clap-host gives it `effect_<N>:midi_out` (`jack_lv2_e2e`: the port is there; no test reads notes from it) | not tested |
| Control ports alone: no audio port and no MIDI port either way; or a MIDI sink, a MIDI input and control ports with nothing out | supported as a pass-through tool, the host's placement: the strip's audio passes through the stage bit for bit with no latency, named `passthrough: host`; the control inputs are parameters and the control outputs read-only parameters read after every block, a MIDI sink's notes arriving through its note input (`lv2_host_test` control only and MIDI sink, `lv2_clap_test` control only and MIDI sink, `jack_lv2_e2e`). Other plugins with no audio output and no MIDI output (CV ports only, a side-chain input only, a time or patch atom port only, a latency port only) are admitted the same way and untested. A plugin with no port at all is refused `hosting.topology.no-audio-output` | not tested |
| Audio, any other layout | supported: per side, side chains are auxiliary; then a declared main group with members (`pg:mainInput`, `pg:mainOutput`) is the main port, else the first group, else for ungrouped ports up to two, as many as the other side's main port is wide (one main port of that width: the other side's main group, or its ungrouped ports; its side chains and auxiliary groups never count), or the first two; every other group is one auxiliary port and every other ungrouped port one mono auxiliary port, in first-member order. The main ports may differ in width (mono in, stereo out). Up to 64 channels a port and 64 auxiliary ports a side, the side's CV ports counted with them; one more is refused `hosting.topology.port-too-wide` or `hosting.topology.too-many-ports`. The adapter does not judge width: the carrier does, the core refusing `hosting.topology.wider-than-strip` at activation on a two-leg lane. Proven by value through `process()` (`lv2_clap_test` layouts): four-two, main-aux, mono-stereo, bands (three auxiliary outputs), four-group-four (four inputs as wide as an output group of four), four-two-two (four inputs against an output group of two and two ungrouped outputs: a main pair and two mono aux), four-side (four inputs against two outputs and two side-chain outputs: the same); by their description (`lv2_host_test` layouts): two-mono, four-four, two-one, sixty-four, cv-sixty-four, empty-main (a main group without members is no main); by their refusal: sixty-five and cv-sixty-five (`too-many-ports`), wide-sixty-five (`port-too-wide`). `jack_lv2_e2e` racks the host fixture's mono-in stereo-out twin as `in_1` / `out_1 out_2` | not tested |
| Port groups (`pg:mainInput`, `pg:mainOutput`, `pg:group`, `pg:sideChainOf`, the group's `rdf:type`) | supported: every group is read, on both sides, by the rules above. A group typed in `port-groups.ttl` (mono, stereo, mid-side, 3.0 to 7.1 wide, the ambisonic groups) whose members carry its designations is ordered by them: a surround group is a `CLAP_PORT_SURROUND` port, its map in CLAP surround ids; a full-order ambisonic group (`AmbisonicBH1P1Group`, `BH2P2`, `BH3P3`) a `CLAP_PORT_AMBISONIC` port in ACN order; a mixed-order ambisonic group a port of no type, its ACNs in the map. Where a port is surround the shim offers `clap.surround`, its `get_channel_map` the group's map and `is_channel_mask_supported` true for that group's own mask only; where a port is ambisonic it offers `clap.ambisonic`, whose `get_config` answers false and whose `is_config_supported` accepts ACN with SN3D only, the one configuration the adapter carries. LV2 port groups declare no normalisation, so the shim states none: the core reads ACN and SN3D through its fallback and marks the port `ambisonic_assumed` (the description's `assumed`), the convention read rather than declared. Any other group, or a typed one whose members lack its designations, stays in port index order: mono or stereo at one or two channels, of no type above two. Tested group types: stereo (main-aux), 5.1 (five-one, by value), `AmbisonicBH1P1Group` (ambi-first, by value), `AmbisonicBH2P1Group` (ambi-mixed, by description); the other types are table entries, no fixture (`lv2_host_test` and `lv2_clap_test` layouts); five-one's map read by the core through `clap.surround`, ambi-first's ACN and SN3D through the core's fallback, marked assumed (`lv2_clap_test` `t_layouts_kinds`) | not tested |
| Control input ports | supported: a CLAP parameter each, id = port index, name, range and default from the TTL (an absent `lv2:minimum` or `lv2:maximum` is -1e9 or 1e9, as a patch parameter's; the default is `lv2:default`, else the minimum, else 0, inside the range: `lv2_host_test` ll midi, `lv2_clap_test` ll midi), written before the block's run (`lv2_clap_test` fixture) | supported: set and read back by `lv2:symbol` through both workers: through omx-clap-host `param_set 0 ratio 8` reads back 8, and the makeup gain set the same way is heard (the own-host page job); through mod-host `gain` set to 0.25 reads back 0.25, and again after the worker is killed and respawned (`jack_e2e.py` own worker) |
| Control output ports | supported: a read-only CLAP parameter each, read back after every block, starting at the port's `lv2:default`, else its `lv2:minimum`, as mod-host starts it, for a plugin that reads its own output (`lv2_clap_test` fixture and props, `lv2_host_test` fixture) | not tested |
| Latency port (`lv2:latency`, `lv2:reportsLatency`) | supported: `clap.latency` (`lv2_clap_test` latency and fixture, `lv2_run_test` pad) | not tested |
| A latency that changes while running | lossy: held until it has read unchanged for `latency_hold_ms`, then one restart; a change that comes back inside the hold is ignored. The restart is CLAP's alone: the LV2 instance stays active and is not reset, so the plugin's history runs on through it, unless the rate, the block lengths the plugin was last told (a shorter block told through `options:interface` included) or a state load held for that activate change (`lv2_clap_test` latency, state; `lv2_host_test` keep). libomx-clap-core's restart after its warm-up stays a full LV2 deactivate and activate (`lv2_clap_test` core) | not tested |
| The plugin's own bypass (`lv2:enabled`, a `bypass` port) | lossy: held at the value that keeps the plugin processing; the host's crossfade is the bypass. Turning the bypass off after a steady bypass resets the plugin (LV2 deactivate then activate, the worker joined before and started after) on the host's control thread, never in the audio path (`lv2_clap_test` fixture, core and worker, `lv2_host_test` fixture). A reset whose worker cannot start again leaves the plugin deactivated: `process()` fails until the next activate, and clap.log says why (`lv2_clap_test` reset) | not tested |
| CV ports (`lv2:CVPort`) | supported: each CV input one mono CLAP audio input after the auxiliary inputs, each CV output one mono CLAP audio output after the auxiliary outputs, not main, counted with the auxiliary ports against their limit of 64 on each side and capped by nothing else: 64 CV ports and no auxiliary port is the limit, one more on either side, alone or with auxiliary ports, is refused `hosting.topology.too-many-ports` (`lv2_host_test` layouts: cv-sixty-four, cv-sixty-four-out, cv-sixty-four-only, cv-sixty-four-only-out admitted; cv-sixty-five, cv-sixty-five-out, cv-sixty-five-only, cv-sixty-five-only-out refused), named by the port's `lv2:name`; every frame of a block is passed both ways, bit-identical with the plugin run directly (`lv2_clap_test` cv, `lv2_host_test` cv), sixteen a side each proven by value (`lv2_host_test` cv many, cv many-out: ams-lv2's multiphase_lfo has sixteen CV outputs). An input the host hands no buffer reads silence | not tested |
| Atom and event ports, MIDI (`midi:MidiEvent`) | supported: one MIDI input and one MIDI output, each a `clap.note-ports` port that prefers the MIDI dialect (the input also takes CLAP note events, below; the output offers MIDI only). Every channel message, sysex and system realtime byte arrives at its own length (a program change or channel pressure is two bytes) at its frame, and a frame past the block is held at its last. An input message of no bytes, or past the atom buffer (at least 1024 bytes; `rsz:minimumSize` is read only for a MIDI port that is the patch port too), is dropped and counted as `midi_in_dropped` (`lv2_host_test` midi run). An output message of up to three bytes, or a sysex, is passed on; anything else is not. omx-clap-host writes the output's messages of up to three bytes to `effect_<N>:midi_out` at their frame (`jack_notes_out_e2e`); a sysex is counted there and not sent, which no test checks (`lv2_clap_test` midi and midi refusal, `lv2_host_test` midi ports and midi run). A second atom MIDI port each way is fed an empty sequence or drained, the first in index order the note path's (`lv2_host_test` midi ports, `lv2_clap_test` two-in and two-out), and a port that takes both MIDI and `patch:Message` is the patch port too (`lv2_clap_test` midi+patch, `lv2_patch_test` MIDI twin). An `ev:EventPort` (the event extension's port, atom's predecessor) that supports `midi:MidiEvent` is read the same way, input and output, over an `LV2_Event_Buffer` of the atom MIDI buffer's bytes, `uri-map` and `event` offered for it: a CLAP note on and a raw MIDI message reach the plugin at their frames and what it writes comes back at its frames, a message past the buffer is dropped and counted as `midi_in_dropped`, and a second event port each way is fed an empty buffer or offered one and never read (`lv2_host_test` event and event run, `lv2_clap_test` event). An event is at most 65516 bytes (its padded length counts in 16 bits): a longer input message is dropped and counted, and the output is read only inside the buffer the plugin was given, in frames, up to its event count, from the data the host handed it (`lv2_host_test` event run and event big buffer). A table whose `midi:MidiEvent` id is past 16 bits, or 0 (a table that could not map it; 0 is the event extension's reference-counted type), refuses an `ev:EventPort` plugin with `hosting.no-realisation` before it is instantiated (`lv2_host_test` event wide table and event zero id). Beside an atom MIDI port, in either index order, the first MIDI port each way is the note path's and the other is fed empty or never read (`lv2_host_test` event mixed). An `ev:EventPort` that supports no `midi:MidiEvent` is refused with `hosting.features.midi-in-fed-empty` (`lv2_host_test` event). An `llext:MidiPort` (ll-plugins' MIDI port, the event extension's predecessor; zynadd declares its MIDI input as one, #284) is read the same way, input and output, over an `LV2_MIDI` buffer (`lv2/core/lv2_ll_midi.h`, the ll header as zyn carries it: each event a double timestamp, a `size_t` size and the bytes) of the atom MIDI buffer's bytes: a CLAP note on and a raw MIDI message reach the plugin at their frames and what it writes comes back at its frames, a message past the buffer is dropped and counted as `midi_in_dropped`, and the output is read only inside the buffer the plugin was given, from the data the host handed it, up to its event count, each stamp a frame (`lv2_host_test` ll midi and ll midi run, `lv2_clap_test` ll midi). The host keeps a `double` of slack past the buffer's capacity holding +inf, because zynadd's reader (`lv2midi_step`) reads the stamp after the last event before it checks the size: on a block filled to the capacity that read lands in the slack and says no further event (`lv2_host_test` ll midi run, the full block). An `llext:MidiPort` is the only MIDI port in its direction: a second one, or an atom or `ev:EventPort` MIDI port beside it in either index order, refuses the plugin with `hosting.features.midi-in-fed-empty` (`lv2_host_test` ll midi, six twins). Only the port class is read; the older `lv2:datatype <…/miditype>` form is not | not tested |
| `time:Position` on the MIDI input (a MIDI input that also supports `time:Position`) | supported: the same object as on a `time:Position` input, by the same rule, at frame 0 of the MIDI input's sequence, before the block's MIDI messages (`lv2_clap_test` atom midi-time) | not tested |
| CLAP note events into the MIDI input | lossy: the MIDI input's `clap.note-ports` port offers the CLAP dialect beside MIDI (MIDI preferred). `CLAP_EVENT_NOTE_ON` is a note on and `CLAP_EVENT_NOTE_OFF` a note off of the same channel and key, the velocity scaled to 0..127 and rounded (a note on never at 0, which MIDI reads as a note off). `CLAP_EVENT_NOTE_CHOKE` is a note off of velocity 0, since MIDI has no choke; an event with a wildcard key or channel, a note expression, and a note on another port are not carried, since a MIDI message names one key on one channel (`lv2_clap_test` atom midi-time) | not tested |
| `time:Position` input (the first sequence input that supports `time:Position` and not `patch:Message`, whatever else it lists, such as `atom:Sequence`) | supported: forged at frame 0 of every block while the transport plays, so the plugin reads each block's frame and beat; while stopped only when the transport changes, an unchanged one forging nothing; no transport, an empty sequence. `time:frame` is the frame count the host's blocks have run (CLAP's steady time), not a song position in frames, which CLAP's transport does not carry. Named by `lv2_clap_test` time: every key and value, the rule, a withdrawal and a tempo-only transport | not tested |
| `patch:` numeric parameters | supported: a `patch:Set` forged before each block's run, `patch:Set` and `patch:Put` read back after it, the ids above the port indices, given in the order of the properties' URIs so that a plugin's ids are the same in every instance (`lv2_patch_test`, `lv2_host_test` atom ports). Earlier versions gave them in lilv's order: for a plugin with two or more such properties the ids may differ, so a session saved with an earlier version may map those parameters differently; the CLAP face lists them as parameters, a write lands before the block and the plugin's own value comes back as an output parameter event (`lv2_clap_test` patch face) | not tested |
| `patch:` messages written as `atom:Blank`, and `patch:Put` with a `patch:body` | supported: an output `patch:Set` or `patch:Put` is read whether its object is an `atom:Object` or an `atom:Blank` (the older name of the same atom, which older plugins forge), and every numeric or text property of a `patch:Put`'s `patch:body` is read as a `patch:Set` of it is (`lv2_clap_test` atom text) | not tested |
| `patch:` file paths and strings (`rdfs:range` `atom:Path` or `atom:String`) | supported through the plugin's own patch port: CLAP has no text parameter, so the adapter's `omx_clap_lv2_patch_text_*` functions list them, write one (a `patch:Set` at frame 0 of the next block) and read back the value the plugin last reported in a `patch:Set` or `patch:Put`. A value is at most 4095 bytes, and with its NUL at most the patch port's buffer less 80 bytes (the buffer is the configured `atom_buffer_bytes`, or the port's larger `rsz:minimumSize`): a longer one is refused with `hosting.patch.too-large`; a property the plugin does not list with `hosting.patch.not-writable`; a write while the previous one waits for its block with `hosting.patch.busy`. A value the plugin reports longer than 4095 bytes before its NUL, or with no NUL within 4096 bytes, is dropped and counted in `patch_dropped`; one of exactly 4095 bytes is read whole. A new LV2 instance (an activate at another rate) is sent the host's last value of each again (`lv2_clap_test` atom text) | not tested |

| An atom output that is neither MIDI nor the patch output (a notify port for the plugin's own GUI) | supported, discarded: up to 16 such outputs, the MIDI outputs after the first counted with them, each offered a buffer of its own every block; what the plugin writes there has no CLAP counterpart and the adapter hosts no LV2 GUI, so it is not passed on (`lv2_clap_test` atom text, `lv2_host_test` atom ports; a fifth is admitted, `lv2_host_test` atom notify-many). One more than 16 is refused with `hosting.features.midi-in-fed-empty`, which no test reaches | not tested |
| The patch input when it lists more than `patch:Message` (LSP's `in_ui`: `atom:Sequence`, `patch:Message`, `time:Position`; dragonfly's `atom:String`, `patch:Message`) | supported: the first sequence input that supports `patch:Message` is the patch input, whatever else it lists; when it also supports `time:Position`, the block's transport object (the same object, by the same change rule, as on a `time:Position` input) is at frame 0 ahead of the block's `patch:Set` messages, and the buffer has room for it (`lv2_host_test` atom ui, `lv2_clap_test` atom ui) | not tested |

### Why a CV port is an audio port

An LV2 CV port carries one float per frame, as an audio port does. The adapter presents it as a CLAP audio port, not
as a parameter-modulation input or output, because only an audio port keeps it exact: CLAP's parameter modulation
(`CLAP_EVENT_PARAM_MOD`) is an event that holds one value from its time on, so a signal that changes on every frame would
be quantised to the events a block carries, and CLAP has no modulation output at all, so a CV output would have nowhere
to go. CLAP has no CV port type either (its draft `clap.cv` extension is not in CLAP 1.2), so the port's type is
`CLAP_PORT_MONO` and its name says what it is. A host that runs the plugin through libomx-clap-core sees a CV input as an
auxiliary input it may bind (`omx_clap_host_bind_aux_input`) and a CV output as an auxiliary output, left unconnected.
